Same three steps, every single turn. The only thing that changes call to call is what's sitting in messages.

Example 03

The agent loop

while (!finished) {
  response = model(messages, tools)

  if (response.toolCalls.length) {
    for (call of response.toolCalls)
      messages.push(executeTool(call))
  } else {
    return response   // unless finish_reason is "length"
  }
}

Two safeguards, two failures

Bounding the loop

MAX_ITERATIONS
A model that never stops asking for tools, until your budget is gone. Common range: 10–20 for most tasks.
TOOL_TIMEOUT_MS
One hung tool call stalling the whole run, with no output at all. Common range: 30–60s for quick calls, 5–10 min for slow-but-legitimate ones like a test suite.

Hitting the cap is information: the task was too big, the tools too weak, or the prompt too vague. And a timeout stops the waiting, not the tool — it may still be running.

History vs. state

The model itself is always stateless — that never changes. This is a different split: of the state the harness keeps across turns, which part does the model actually get to see?

The model's entire view of the world. Every token is sent, and paid for, on every single call.
AgentState
Runtime bookkeeping — iteration count, which files were already read, the last test result. The model never sees it. Costs nothing.

What it costs

Append-only,
for a reason

Turn 1

Turn 5
Turn 7

Turn 12
Final context: 7,500 tok
Total billed: 57,000 tok

Each bar is one call's full context — every call resends everything before it, not just what's new. That's why cost is closer to quadratic than linear.

Why append-only? Editing an earlier turn breaks the prefix match caching depends on. Appending is the only move that's always cache-safe.

Not a harness feature — a provider one

Where does the cache
actually live?

Where
On the provider's own servers — not in your harness, not on disk anywhere you control.
What
The model's processed internal representation of a token prefix, keyed by a hash of its exact content.
How long
Anthropic: 5 minutes by default, reset on every hit — a 1-hour option exists at higher write cost.
The price
A cache write costs more than normal (1.25×). A cache hit costs far less (0.1× — a 90% discount).
What a prefix looks like
system  You are a coding agent…
tools   search_code, read_file,
        edit_file, run_tests
user    Refactor getPokemonByName
asst    → search_code(…)
tool    found pokedex.ts
── cache breakpoint ──
asst    ← new, full price
key = hash(everything above the line)
Change one character up there — a timestamp, a different model — and it's a new hash: full miss.
A concrete example

What's inside
one single call

One turn = one pass through the loop = one call to the model. Here's everything inside the 4th call, piece by piece:

Tools · 500
System prompt · 2,000 tok
Already sent in turns 1–3 · 1,500
New this turn · 300
←  cached: written once, then read at 0.1× while the prefix stays identical  →
full price

Everything except the last sliver is byte-identical to what call 3 already sent — that part is read from cache at a discount, as long as the entry is still alive. Only the new sliver costs full price.

Why, not how — the how is next session

Caching makes tokens cheaper.
Compaction makes fewer of them exist.

Still a bill
A cache hit is 90% off, not free. A conversation that never stops growing still grows its bill — just more slowly.
Hard ceiling
Every model has a maximum context size. Caching is a pricing trick — it does nothing to stop history from eventually hitting that wall.
Quality, not just cost
Models get measurably worse at finding what matters buried in a very long context ("lost in the middle") — independent of whether it's affordable.

Caching is a cheaper storage tier. Compaction is deleting what you don't need. Different jobs — you want both.

The two are not independent

Compaction always
costs one cache miss.

Compacting rewrites the prefix, so the cache hash no longer matches — the very next call is a guaranteed miss, billed at full write price.

But it's a one-time reset, not a permanent loss. The new, shorter history becomes a fresh prefix — caching resumes normally from there. That's exactly why compaction is rare and deliberate: do it constantly, and you're paying the miss tax on every call.
More calls, more 429s

Two kinds of retry

Transport · provider.ts
429, 5xx, dropped connection, timeout. The harness decides. Backoff, Retry-After, jitter. The model never sees it.
Semantic · the loop
A tool returned { ok: false }. The model decides: try again, or take another route. Session 6.
search_code
safe to retry ·
send_email / create_ticket
not safe — can double-send

Semantic retries assume the tool is idempotent. Not all of them are.

A rate limit carries nothing the model can act on. A failed tool carries exactly what it needs. Different layers, on purpose.
