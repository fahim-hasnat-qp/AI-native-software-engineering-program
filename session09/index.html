Tonight's map — one index, three questions

Same corpus. Three different failures.

Fails on matching
“What changed in the export API in v4.2?”
Embeddings blur exact tokens. To the model, v4.2 and v4.1 mean the same thing — a version number.
Fails on the query
“Why are people quitting our survey halfway?”
The document that answers this doesn't use a single word from the question. It says "break-off," not "quitting."
Fails silently
“How many responses do I get on the free plan?”
Retrieval succeeds. It returns the archived 2024 pricing page at 0.87 similarity, and the model answers from it confidently.

One vector store — our help center, API docs, and pricing pages. Notice the failures get quieter left to right, which is why the fixes get more expensive.

Why dense retrieval misses

Semantic search is lossy on the literal.

Dense — embeddingsSparse — BM25
Matches meaning and paraphraseMatches exact tokens
"car" ≈ "automobile""v4.2" = "v4.2", or nothing
Rare terms get averaged awayRare terms score highest
Survives zero word overlapDies without word overlap

These aren't competing philosophies. They fail in opposite directions.

So don't choose

Run both retrievers. Fuse the ranks.

Two candidate lists from two very different notions of "similar," merged into one ordering.

In code

Two retrievers, one ensemble.

from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever

bm25 = BM25Retriever.from_documents(docs)
bm25.k = 5

dense = vectorstore.as_retriever(search_kwargs={"k": 5})

hybrid = EnsembleRetriever(
    retrievers=[bm25, dense],
    weights=[0.4, 0.6],          # tune on your own eval set
)

results = hybrid.invoke("What changed in the export API in v4.2?")

The weights are the knob. Lean sparse for technical corpora full of identifiers; lean dense for prose.

The real mismatch

Same topic. Zero shared words.

The questionHow users ask

The documentHow researchers write

"Break-off rises sharply after twelve minutes. Matrix grids on mobile lose the most respondents."

quitting ≠ break-off

halfway ≠ twelve minutes

The document is the answer. The retriever has no way to know.

Hypothetical Document Embeddings

Search with the answer you don't have yet.

Ask the LLM to invent a plausible answer first. Embed that. Now you're matching answer against answer.

What the model invents

A fake answer, in the right words.

The draft the LLM writes
Respondents break off when a survey runs too long. Break-off climbs steeply past the ten-minute mark, and long matrix grids on mobile drive the highest abandonment. Respondent fatigue is the most common cause.
Why that helps
"break-off", "respondent", "matrix grid", "fatigue" — the words our documents actually use. None of them were in the question. Now we can search with them.

Ten minutes or twelve? The draft got it wrong. It doesn't matter — we're using it to search, not to answer.

The part that feels wrong

The hypothetical answer doesn't have to be true.

It only has to land in the right neighborhood of embedding space. Wrong facts, right vocabulary — and the retrieval improves anyway.

In code

One extra generation before the search.

HYDE_PROMPT = """Write a short, confident passage that answers the
question as if it came from our internal documentation.
Do not hedge. Do not say you are unsure.

Question: {question}
Passage:"""

def hyde_retrieve(question, k=5):
    draft = llm.invoke(HYDE_PROMPT.format(question=question)).content
    return vectorstore.similarity_search(draft, k=k)   # search with the draft

"Do not hedge" matters. A hedged draft full of "it depends" embeds toward nothing in particular.

Where HyDE stops

A confident draft about the wrong thing.

Ask about a product the model has never heard of and it will still write you a fluent passage — about something else entirely. HyDE doesn't degrade gently; it retrieves the wrong neighborhood with full confidence.

And notice what both fixes have in common: they make retrieval better, but neither ever looks at what came back.

The missing step

Grade the documents before you generate.

Correct
Use it — but trim it
Split into knowledge strips, drop the irrelevant ones, recompose. Less noise in the prompt.
Ambiguous
Use it, and go looking
Keep what you have, add a second source. The blend covers partial relevance.
Incorrect
Throw it out
Discard everything retrieved, rewrite the query, and fall back — usually to web search.

A small, cheap model does the grading. It's a classification job, not a reasoning one.

In code

A grader, then a branch.

GRADER = """Is this document relevant to the question?
Answer with one word: correct, ambiguous, or incorrect.

Question: {q}
Document: {d}"""

def corrective_retrieve(question):
    docs = hybrid.invoke(question)
    grades = [grader.invoke(GRADER.format(q=question, d=d.page_content)) for d in docs]

    if all(g == "incorrect" for g in grades):
        return web_search(rewrite_query(question))       # discard and go elsewhere

    keep = [d for d, g in zip(docs, grades) if g != "incorrect"]
    if any(g == "ambiguous" for g in grades):
        keep += web_search(rewrite_query(question))      # supplement

    return keep

Grade documents in parallel, not in a loop, or you pay K sequential round trips per question.

The bill

Every fix costs a round trip.

HybridNone — BM25 is localMilliseconds
HyDE1, before every retrievalOne full generation

Hybrid is nearly free, so it's the default. HyDE and CRAG are choices you justify.

The line to remember

Naive RAG retrieves. Advanced RAG decides.

Decide how to search, decide what to search with, and decide whether to trust what came back.
