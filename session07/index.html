HNSW, the simple version first

You don't fly Dhaka to Denver directly.

There's no direct flight — there never has been. The actual fastest real route is a single big jump through one major hub, then a precise final leg.

Dhaka (DAC)
→
Istanbul (IST) — the hub
→
Denver (DEN)

One big jump to a well-connected hub, then a direct final leg to the exact destination. That's the entire idea behind HNSW — before it even needs a technical diagram.

Same idea, as a graph

A few "hub" points. Everyone else, local.

Real graphs have more than one Istanbul — a handful of well-connected points, not just one. The three highlighted points are the same points, top and bottom — just well-connected enough to also serve as hubs. A search starts among the hubs, then drops straight down to the local layer once it's in the right neighborhood.

Same shape as the Dhaka-Denver story — one big jump to a hub first, precise only at the very last step.

A question worth asking

Doesn't this sound like a B-Tree?

B-Tree — finding "G"
  • A–Z → split → A–M | N–Z
  • A–M → split → A–H | I–M
  • A–H → split → A–D | E–H
  • E–H → check → E, F, G, H

✓ Found G — guaranteed correct

HNSW — finding a nearest vector
  • Start among the hubs → jump to the closest-looking one
  • Check its neighbors → move only if one looks closer
  • Drop to the local layer at that position
  • Check nearby neighbors → return the best one found

≈ Best found — usually correct, not guaranteed

The difference isn't a design flaw — letters have a total order, so "G is after E" is always true and lets you throw away a whole branch forever. Vectors have no such order, so HNSW can only greedily walk toward whatever looks closest right now.

Today's deliberate pick

For this demo: Chroma.

Lightweight and simple — not "the" vector database, just today's tool. It can run fully in-process, but tonight it's running as a small local server, since that's what lets us talk to it from JavaScript.

Live Demo

Building real semantic search, live
Step 1 — Client & Collection

Client → Collection → Documents + embeddings.

import { ChromaClient } from "chromadb";

const client = new ChromaClient({ path: "http://localhost:8000" });

const collection = await client.createCollection({
  name: "documents"
});

Requires a Chroma server already running (chroma run --path ./chroma_db) — unlike Python's client, which needs no server at all.

Step 2 — Add real documents

Engineering docs, with metadata.

await collection.add({
  ids: ["doc1", "doc2", "doc3", "doc4"],
  documents: [
    "Redis is used for caching frequently accessed data.",
    "RabbitMQ provides async communication between services.",
    "PostgreSQL connection pools reduce connection cost.",
    "Kubernetes automatically restarts failed containers."
  ],
  metadatas: [
    { technology: "redis" },
    { technology: "rabbitmq" },
    { technology: "postgres" },
    { technology: "kubernetes" }
  ]
});
Step 3 — Query without saying the answer

"How can I improve database
connection performance?"

const results = await collection.query({
  queryTexts: ["How can I improve database connection performance?"],
  nResults: 3
});

Notice — PostgreSQL was never mentioned. It comes back anyway.
